JukeBar · internal reference

System Architecture

Three codebases, one house rule: the host app is the source of truth. Everything else — relay, browsers, this document — is downstream of whatever iOS or Android says is true right now.

Repos: JukeBar (iOS) · spotonjukebar (Android) · jukebarweb (Render) Updated: 2026-07-08 Lives at: docs/architecture.html in jukebarweb

01 The three codebases

Same product, three runtimes. iOS and Android each ship a full host app — playback, an embedded HTTP server, and a kiosk UI — that runs unattended on a device at the bar. jukebarweb is the only piece that isn't installed anywhere; it's a hosted relay that lets the host be reached over the internet instead of just the bar's own Wi-Fi.

iOS

JukeBar (~/dev/giffy/JukeBar)

Swift / SwiftUI. Embeds Swifter as its HTTP server. Plays back through Apple Music via MusicService.

Android

spotonjukebar (~/dev/giffy/spotonjukebar)

Kotlin / Jetpack Compose. Embeds NanoHTTPD as its HTTP server. Plays back through the Spotify Web API via PlaybackCoordinator.

Relay

jukebarweb (this repo, on Render)

Python / FastAPI, single main.py. Two jobs: relay messages between hosts and internet customers, and run the public jukebars.com community/discovery pages.

Nothing about a bar's state is stored durably in the relay — BarSession is an in-memory object that's rebuilt from scratch every time the host re-registers. If jukebarweb restarts, every bar just looks briefly offline until its host's next 5-second sync catches up.

05 How data actually moves

Four flows worth knowing cold — the rest of the system is variations on these.

AHost boot & the 5-second sync loop

1

Host registers once at launch — AppState.hostRegisterOnRelay() / RelayService.register() — sending full catalog, bar details, and settings to POST /api/host/register.

2

jukebarweb replaces the bar's BarSession in _bars wholesale. Nothing is merged — every register is a clean slate.

3

Host then calls POST /api/host/sync every ~5s with played/approved ids and the current up-next queue; the response carries back any pending_actions queued by an admin.

BAdmin flips a setting

1

Admin (LAN) posts straight to the host's own /api/admin/settings — takes effect immediately, no relay involved. Admin (Internet) instead posts to jukebarweb's POST /api/bar/{id}/settings, which queues a pending_action and also optimistically patches its own in-memory BarSession so the admin page doesn't see a stale value for the next 0–10s.

2

Host picks up the pending action on its next sync response and updates its local BarDetails / HostConfig.

3

Host re-registers with the new state, which becomes the new canonical value everywhere.

CA customer requests a song

1

Customer submits from whichever surface they're on — kiosk, Wi-Fi page, or jukebars.com — to /api/request (host) or /api/bar/{id}/request (relay).

2

Approval mode is derived from two flags, never a separate enum: stripe_enabled and bartender_enabled. Both off means free and auto-accepted immediately; either on means it lands in the bartender's pending queue.

3

Host injects approved song ids straight into PlaybackCoordinator / MusicService, and reports it back up through the next sync so the relay's up-next queue matches.

DStripe payment vs. "stop taking requests"

1

Customer hits Pay with Card, which calls create-payment-intent — no money has moved yet, so this is freely rejectable.

2

If accepting_requests is false, both /request and /create-payment-intent return 403 immediately (within one ~5s poll, the button itself disappears on every customer surface).

3

payment-confirmed is the one call that is never gated — by the time it fires, Stripe has already charged the card, so the request is honored regardless of the flag. A late straggler gets refunded in cash by the bartender, not by code.
