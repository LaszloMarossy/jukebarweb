JukeBar · internal reference

System Architecture

Three codebases, one guiding architectural principle: the host app is the source of truth. Everything else - host display, HTML served by host or relay through browsers - is downstream of whatever iOS or Android says is the true state right now.

Repos: JukeBar (iOS) · spotonjukebar (Android) · jukebarweb (Render) Updated: 2026-07-11 This doc lives at: docs/architecture.html in jukebarweb

01 Three codebases, four runtimes

iOS and Android each ship a full host app - playback, an embedded HTTP server to serve client devices through WIFI or Hotspot, and a kiosk UI for requests on the host device.

The hosts can run unattended on a device at the bar, either in interactive mode (when customers can make requests right on the host device), in a remote mode (where customers make requests on their own devices after photographing a QR code displayed on the host screen), or in a mixed mode (being able to do either of the previous).

jukebarweb is the only codebase that isn't installed anywhere a customer can see; it runs scripts twice a day to interact with external APIs (on a home mac, to collect genre profiling for the uploaded playlists), and it also serves the community pages for JukeBars (on jukebars.com).

iOS

JukeBar (~/dev/giffy/JukeBar)

Swift / SwiftUI. Embeds Swifter as its HTTP server that serve the Admin/Bartender/Customer pages; plays back Apple Music via MusicService; manages incoming requests from and serves updates to all its Admin/Bartender/Customer all clients; answers Now Playing and Up Next information to client polls.

Android

spotonjukebar (~/dev/giffy/spotonjukebar)

Kotlin / Jetpack Compose. Embeds NanoHTTPD as its HTTP server that serve the Admin/Bartender/Customer pages; Plays back Spotify through its Web API via PlaybackCoordinator; manages incoming requests from and serves updates to all its Admin/Bartender/Customer clients; answers Now Playing and Up Next information to client polls.

Relay

jukebarweb(this repo, on Render)

Python / FastAPI, single main.py. Houses the customer/admin/bartender pages and accommodates their requests in internet mode; serves the public jukebars.com community/discovery pages and APIs; the same codebase houses the scripts to run last-fm related scripts (for now being run on a dedicated home Mac)

Home Mac Server

some of the code on jukebarweb repo - (profile_daemon.py)

are now being run on a physical Mac at home (genre-profiling loop as a LaunchAgent - it never talks to main.py but to GCS directly); this part of the code can be run independently of the rest of the codebase, on any environment. The home Mac now runs other jobs for other projects as well...

Nothing about a bar's state is stored durably in the relay - BarSession is an in-memory object that's rebuilt from scratch every time the host re-registers. If jukebarweb restarts, every bar just looks briefly offline until its host's next 5-second sync catches up. The bar's last three uploaded playlists, and its profiled genre data is the exception: it lives in GCS, outside both processes, which is exactly why two independent runtimes can share/work on it without ever calling each other.

05 How data actually moves

Four flows worth knowing cold - the rest of the system is variations on these.

AHost boot & the 5-second sync loop

1

Host registers once at launch - AppState.hostRegisterOnRelay() / RelayService.register() - sending full catalog, bar details, and settings to POST /api/host/register. This is strictly the internet-relay registration that lets jukebars.com customers browse/request - it's separate from the community-map opt-in (POST /api/map/register, flow E below), which any bar can call regardless of connection mode.

2

jukebarweb replaces the bar's BarSession in _bars wholesale. Nothing is merged - every register is a clean slate. (The "keep the 3 most recent, same-name refreshes" playlist logic you may be picturing is a different thing entirely - that lives in map_register()'s _map_entries/GCS, not here; see flow E.)

3

Host then calls POST /api/host/sync every ~5s - this is the main two-way channel. Host→relay: played_request_ids, approved_request_ids (Android bartender-screen approvals), and the authoritative up_next queue. Relay→host: requests (new pending customer requests since last sync) and actions (queued pending_actions - approve/deny/control/settings_update/stop_session - which are cleared from the queue once sent).

BAdmin flips a setting (any admin surface - kiosk-native, LAN, or Internet)

1

Admin (LAN) posts straight to the host's own /api/admin/settings - takes effect immediately, no relay involved. Admin (Internet) instead posts to jukebarweb's POST /api/bar/{id}/settings, which only queues a pending_action (tagged with a bumped per-field version number in BarSession.settings_version) - it does not patch bar.stripe_enabled/bartender_enabled itself; the field is marked pending in settings_pending until the host confirms. admin.html/bartender.html lock that toggle (dimmed, unclickable, "··· updating") the instant they click, and every other Internet client polling the same bar sees the same lock via settings_pending in bar_catalog()/bartender_requests() - concurrent changes to the same field are queued, not rejected (last one applied wins). Admin (kiosk-native) - AdminView.swift / AdminScreen.kt - skips HTTP entirely and writes the local config in-process.

2

Host picks up the pending request for an action from its next sync response and updates its local BarDetails / HostConfig, remembering the action's version tag. (Kiosk-native admin already did this in step 1, so this step is a no-op for that path.)

3

Host echoes its current settings + the version tag back on every POST /api/host/sync call from now on, unconditionally - not a one-shot confirmation. jukebarweb only applies an incoming echo if its version is newer than settings_confirmed_version, then clears settings_pending for that field. This makes a single dropped sync self-heal on the next one 5s later (no ack handshake needed) and makes a stale echo for a since-superseded request harmless (its version is too low to win). Separately, pushPaymentSettings() / propagateBarDetails() still refreshes the host's own local /api/catalog//api/nowplaying cache immediately for LAN/kiosk pollers, and re-registers with POST /api/host/register if in internet mode.

CA customer requests a song, free or pay-to-bartender (the Stripe/CC path is flow D - it skips the pending queue entirely)

1

Customer submits from whichever surface they're on - kiosk, Wi-Fi/hotspot page, or jukebars.com - to /api/request (host) or /api/bar/{id}/request (relay).

2

Approval mode is derived from the combination of two flags: stripe_enabled and bartender_enabled. Both off means free and auto-accepted immediately; either on means it lands in the bartender's pending queue. This only describes the free/pay-to-bartender path - a Stripe/CC request never goes through this pending queue at all, regardless of these flags (see flow D: payment-confirmed creates an already-paid=True request that the host auto-injects on sight).

3

Host when requests are either approved by bartender, OR are paid with CC, the code injects approved song ids straight into PlaybackCoordinator / MusicService, and reports it back up through the next sync so the relay's up-next queue matches. The same in-process update also flows into the host's own LAN /api/nowplaying / /api/init responses immediately, so Wi-Fi/hotspot clients see it on their next poll without waiting on the relay round trip.

DStripe payment vs. "stop taking requests"

1

Customer hits Pay with Card, which calls create-payment-intent - no money has moved yet, so this is freely rejectable.

2

If accepting_requests becomes false in the meantime, both /request and /create-payment-intent return 403 immediately (within one ~5s poll, the button itself disappears on every customer surface).

3

payment-confirmed is the one call that is never gated - by the time it fires, Stripe has already charged the card, so the request is honored regardless of the flag. If the bartender insists and can not let those late songs play out, the late straggler can get refunded in cash by the bartender, not by code (bartender still sees auto-approved CC requests coming in on its admin screen).

EGenre profiling - the full round trip through GCS and back to the host

1

Host calls POST /api/map/register whenever a bar opts into their bar and their latest 3 playlists (bands only) being seen on the public map - playlist name, note, and the 2 list (with per-artist song counts). This is separate from the register/sync loop; it only fires on setup or playlist change, not every 5s.

2

jukebarweb's map_register() merges this into _map_entries and immediately calls _save_map_entries(), writing the whole table to map_entries.json on GCS via gcs_store.py - so far, no Last.fm call and no Home Mac Server involvement at all.

3

Home Mac Server's profile_daemon.py, on its own ~5-minute cycle, reads that same map_entries.json, diffs it against what it profiled last time, and calls Last.fm for any artist not already in band_cache.json. It writes the result back to GCS as map/{bar_id}/profile.json (and a per-bar artist_genres.json - genre + top tags per artist).

4

jukebarweb never talks to Home Mac Server directly - it just polls its own GCS read on a timer (_maybe_refresh_profiles(), every PROFILE_CACHE_TTLs) and caches the result in _bar_profiles, which is what GET /discover and GET /api/bar/{id}/genres actually serve.

5

Host fetches /api/bar/{id}/genres after registering (retrying if profiling isn't done yet) and uses it to color band bubbles in its own catalog browser. That colored genre map then gets folded into the host's own LAN catalog responses and its relay register/sync payload - so a Wi-Fi customer and an internet customer both end up seeing the same colors, but both got them by way of the host, not by asking jukebarweb directly.
