# jukebar — Product Specification

> **Architecture is in DECISIONS.md.** This file covers product behaviour (what it does); DECISIONS.md covers implementation (how and why).

---

## Overview

A self-contained jukebox system running entirely on one iOS device. It plays an Apple Music playlist, lets customers submit song requests by scanning a QR code, and gives bartenders a browser-based interface to approve/deny requests. The device is its own server — no internet required, no cloud services, no external dependencies. Payments are handled manually by the bartender; the app has no payment infrastructure.

---

## System Surfaces

### 1. JukeBar — iOS app (Swift/SwiftUI)
The one and only native app. Runs on the bar's iPhone/iPad. Handles playback, displays now playing, runs the embedded HTTP server, shows the QR code, and has a PIN-protected admin mode.

Path: `/Users/laszlo/dev/giffy/JukeBar/JukeBar/`

### 2. Customer Web App (HTML/JS, served by JukeBar)
Customers scan the QR code → browser opens on their phone → browse artists/albums/songs, pick up to 3, submit request, track status. No install required. Must be on the same WiFi as the host device.

URL: `http://<device-LAN-IP>:8080/request`

### 3. Bartender Web App (HTML/JS, served by JukeBar)
Bartender opens a URL on any browser on the same WiFi → pairs with PIN → approves/denies requests. No install required.

URL: `http://<device-LAN-IP>:8080/bartender`

### 4. Embedded HTTP Server (Swifter, inside JukeBar)
Runs on port 8080, binds to `0.0.0.0` (all interfaces). Serves both web apps and handles all API requests. All logic is on-device. No auth tokens — local network presence is the security boundary.

### 5. Local Storage (`Documents/` on the device)
JSON files in the app's `Documents/` folder. No database. Reports accessible via iOS Files app; shareable via AirDrop/email.

## Identity

### `jukebar_id` — permanent
- UUID generated once on first launch, stored in UserDefaults forever
- Identifies this physical device/installation through all restarts

### `playlist_id` — per session
- UUID generated locally at the start of each session
- Rotates on: app restart, admin pressing "Stop for the time being", or 30-minute pause timer expiry
- Does not persist; a new one is always generated on each rotation

### Customer Identity
- UUID generated by the customer web app on first visit, stored in browser `localStorage` forever
- No login required
- Customer optionally enters a friendly name that travels with their requests

## Host App — Behaviour

### Setup Wizard (shown on every cold launch)
1. Authorize Apple Music access
2. Pick an Apple Music playlist
3. Enter bar name
4. Set PIN (4–6 digits; leave blank to keep existing PIN, or enter a new one to reset it if forgotten)
5. Choose request handling:
   - **Bartender approval** — customers use QR on their own devices; requires network permission grant
   - **Auto-accept** — requests entered on the host device only; all auto-approved immediately
6. Set currency symbol/prefix (default `$`; accepts `€`, `Huf`, etc.), per-song price, and 3-song bundle price; optional auto-accept timer
7. Catalog loads in background → CatalogIndex built → server starts → QR displayed

All fields pre-filled from the previous session's config; going through the wizard again starts a fresh session.

### Network Setup
- **WiFi:** customers join the same WiFi network as the iPhone. Requires AP/client isolation to be **disabled** on the router (recommended: use a dedicated guest network with isolation off). Reboot router after changing isolation settings.
- **Personal Hotspot:** customers join the iPhone directly (no router). Bypasses all AP isolation issues. Requires cellular.
- **Local only:** no remote connections; all requests auto-accepted at the host device.

`NWPathMonitor` watches for network changes; server restarts automatically when WiFi interface changes.

### Kiosk Mode
- `UIAccessibility.requestGuidedAccessSession()` locks device to the app
- Exit: triple-click side button + iOS Guided Access PIN
- Admin features protected by a separate app PIN (long-press bar name)

### Security Model
- **Physical access = admin trust.** The device lives behind the bar; anyone who can reach it is assumed to be staff.
- **PIN recovery:** run the setup wizard again (End Session → restart) and enter a new PIN at step 4. The new hash replaces the old one.
- **Reinstall is not a bypass.** Installing from the App Store or restoring from iCloud requires Apple ID authentication (Face ID / Touch ID / Apple ID password). An attacker with physical access but without the Apple ID credentials cannot reinstall to wipe the PIN.
- **Future hardening (deferred):** `LocalAuthentication` / Face ID challenge before entering admin mode; would add a second factor on top of the app PIN.

### Public Layer (anyone can touch the screen)
- Now Playing: artwork, title, artist
- Up Next: approved requests in order, then "shuffle continues…"
- Browse Catalog: A–Z letter grid → artist → album → song drill-down, or free-text search
- Build Request: tap up to 3 songs, enter name, submit
- Header: grapefruit logo + "JukeBar [bar name]" with rainbow letter coloring; pricing shown as "Requests: [currency] X/song · [currency] Y/3 songs"

### Admin Layer (PIN required, long-press bar name)
- Playback controls — play/pause, skip forward/back, now-playing album art and title
- **Stop for the time being** — pauses music and rotates the session (new `playlist_id`, new QR code generated); old customer QR codes are invalidated immediately. Also triggered automatically after 30 minutes of continuous pause.
- Refresh Catalog — re-reads Apple Music playlist, rebuilds CatalogIndex, invalidates server cache
- Approval mode toggle — switch between "Bartender approval" and "Auto-accept" mid-session without restarting
- Change Mode — reset `preferredNetworkMode` and return to the network setup screen
- Reports — list, share (AirDrop/email), delete session CSVs
- Server diagnostics — LAN IP, server status, self-test button
- End Session — archives current session to CSV, returns to setup wizard

### Session Rotation Triggers
A new `playlist_id` is generated (session rotates) in three situations:
- **App restart** — always rotates; setup wizard runs, catalog reloads
- **Stop button** — admin presses "Stop for the time being" in the iOS admin panel or the bartender/admin web UI
- **30-minute pause timer** — if music has been paused continuously for 30 minutes, `stopSession()` fires automatically

### On Restart / New Session
1. Generate new `playlist_id`
2. Archive old session: compile requests → CSV → save to `reports/`; delete old CSVs older than `report_retention_days`
3. Wipe old `{playlist_id}/` folder
4. Create fresh session folder with new `session.json`
5. Load catalog → build `CatalogIndex` → pre-serialize for HTTP serving
6. Start server (if networked), show QR with new `?s={playlistId}` embedded

On Stop (without restart): steps 1–4 run, then the relay (internet mode) is re-registered and the server continues running on the same port with the new session.

### Playback Engine
- Source: single Apple Music playlist (songs downloaded to device)
- No internet needed for playback if songs are pre-downloaded
- Player: `MPMusicPlayerController.applicationQueuePlayer` with `AVAudioSession(.playback)` and `UIBackgroundModes: audio` so playback continues on the lock screen
- Queue shape at all times:
  ```
  ▶ Now playing
  1. Approved request with jump flag ⚡  ← plays immediately after current
  2. First approved request (song 1)
  3. First approved request (song 2, if any)
  4. Second approved request...
  5. Shuffle from playlist             ← fills gaps
  ```
- Skip: `skipToNextItem()` / `skipToPreviousItem()` — requires the initial `setQueue()+play()` to have been called from an `.onAppear` context (see DECISIONS.md for the critical UI pattern)
- Shuffle order: playlist items shuffled once at session start into a `shuffledItems: [MPMediaItem]` array; order is fixed for the session
- Request injection: approved songs are prepended into the live player queue via `player.prepend()`. A `nowPlayingItemDidChange` observer tracks which approved songs have started playing and promotes the next batch. See DECISIONS.md for the two-level queue design.

## Bartender Web App — Behaviour

### Entry
- Bartender joins bar WiFi/hotspot, opens `http://<device-IP>:8080/bartender`
- URL shown in the host admin UI; also accessible as QR code

### Pairing (every session)
- Enter name + PIN
- First to pair → admin for the session; subsequent → pending until admin approves
- Re-pair on every host restart; no persistent accounts

### Main View — Pending Requests
- Polls every 20s
- Each row: customer name, songs, price, time
- **Approve** → `approved`; songs join end of queue
- **Approve ⚡** → `approved_jump`; plays immediately after current song
- **Deny** → `denied`

## Customer Web App — Behaviour

### Entry
- Scan QR or type URL → browser opens
- `customer_id` UUID generated on first visit using `uuid4()` (Math.random-based; `crypto.randomUUID` is unavailable over plain HTTP), stored in `localStorage` forever
- Catalog loaded from `/api/catalog` (`Cache-Control: no-store`); renders immediately from `localStorage` on repeat visits while background refresh happens

### Browse & Request
- **A–Z grid:** 27 letter/# buttons (4-column grid). Dimmed if no artists start with that letter.
- **Artist bubbles:** tap a letter → pill-shaped bubbles for all matching artists. Sort order: "The " prefix stripped, accented characters normalized (É→E) before grouping and sorting.
- **Albums:** tap an artist → album rows with song counts.
- **Songs:** tap an album → song rows with checkboxes. Max 3 selected; 4th song greys out remaining.
- **Search:** type in search bar → flat filtered results across title/artist/album/genre (overrides hierarchy).
- Basket bar: `[currency] [amount]` (amount highlighted in coral); tap → slide-up modal
- Modal: song list, total price, name input → Submit → POST `/api/request` → confirmation popup

## API — Embedded Server Routes

| Route | Description |
|---|---|
| `GET /request` | Customer web app HTML (cached 1hr) |
| `GET /bartender` | Bartender web app HTML (cached 1hr) |
| `GET /api/health` | Health check — `{"status":"ok"}` |
| `GET /api/init?s={playlistId}` | Customer session init — **validates `?s=`**, returns 403 if stale |
| `GET /api/catalog` | Catalog + pricing + currency — pre-built bytes, `no-store` (no session check) |
| `POST /api/request?s={playlistId}` | Submit song request — **validates `?s=`**, returns 403 if stale |
| `GET /api/requests?status=` | List requests by status |
| `GET /api/request/{id}?s={playlistId}` | Single request status — **validates `?s=`**, returns 403 if stale |
| `POST /api/request/approve` | Approve request (`jump: true` for jump queue) |
| `POST /api/request/deny` | Deny request |
| `POST /api/admin/stop` | Rotate session — pauses music, generates new `playlist_id` and QR |
| `POST /api/bartender/pair` | Pair bartender via PIN |
| `GET /api/bartender/status?bartender_id=` | Check bartender approval status |
| `GET /api/bartender/list` | List bartenders |
| `POST /api/bartender/approve` | Admin approves bartender |
| `POST /api/bartender/deny` | Admin removes bartender |
| `GET /api/reports` | List report CSVs |
| `GET /api/reports/{filename}` | Download report CSV |
| `DELETE /api/reports/{filename}` | Delete report |

**Session validation (WiFi/hotspot mode):** Customer-facing endpoints marked above validate the `?s={playlistId}` query parameter against the active session. A mismatch returns `403 {"error":"session_expired"}`. The customer web app detects this and shows a "Session ended — scan the new QR code" overlay. All other endpoints (catalog, bartender, admin, nowplaying) have no token check — local network presence is their security boundary.

## Pricing

| Basket | Price |
|---|---|
| 1 song | [currency] X |
| 2 songs | [currency] X × 2 |
| 3 songs | [currency] Y bundle (set independently, typically less than 3 × X) |

Currency (ISO 4217 code) configured once at setup — used for both display and Stripe payment processing. One field; no separate "bar currency" vs "Stripe currency".

### Stripe payments (optional)

When Stripe keys are provided, a **Pay Online** button appears next to Submit. The customer enters card details via Stripe.js Elements; the host creates the PaymentIntent server-side (secret key never leaves the device).

**Minimum charge amounts** — Stripe enforces a per-currency floor. Additionally, if the Stripe account settles in a different currency (e.g. a Hungarian business settles in HUF), the converted settlement amount must also clear the HUF floor (175 HUF). At current rates, PLN 2.00 ≈ 160 HUF which falls below it — set prices with enough margin.

Full table: [docs.stripe.com/currencies#minimum-and-maximum-charge-amounts](https://docs.stripe.com/currencies#minimum-and-maximum-charge-amounts)

The setup wizard shows the Stripe minimum for the selected currency as a hint next to the price field, with a link to the full table.

### Apple Pay and Google Pay (wallet payments)

Stripe supports Apple Pay and Google Pay through its **PaymentElement** UI, which automatically shows the appropriate wallet button based on the customer's device. This replaces the manual card entry form and lets customers pay with a single Face ID / fingerprint tap.

**Google Pay** — no setup required beyond Stripe keys. Works automatically on Android/Chrome over HTTPS.

**Apple Pay** — requires a one-time domain verification per Stripe account:

1. Bar owner logs into their Stripe Dashboard → **Settings → Payment methods → Apple Pay**
2. Click **"Add new domain"** and enter `jukebars.com`
3. Click **Verify** — the domain association file is already served by the JukeBar relay, so verification passes immediately (no file download or hosting required on the bar's part)
4. Apple Pay now appears on iPhones when customers pay via relay/internet mode

Multiple bar owners can independently verify the same domain against their own separate Stripe accounts.

**Availability by connection mode:**

| Mode | Apple Pay | Google Pay | Card entry |
|---|---|---|---|
| Relay / internet (HTTPS) | ✓ after domain verification | ✓ automatic | ✓ |
| WiFi / hotspot (HTTP, local IP) | ✗ requires HTTPS + verified domain | ✗ | ✓ |
| Local only | ✗ | ✗ | — (cash only) |

**Implementation note:** The current customer web app uses `stripe.confirmCardPayment()` with a `CardElement`. Switching to `PaymentElement` (a single component swap in customer.html) would unlock Apple Pay, Google Pay, and any future Stripe-supported methods automatically. The backend (PaymentIntent creation) requires no changes.

## Licensing

JukeBar is a queue management and request tool — it has no opinion on the content of the playlist it plays. Responsibility for music licensing rests entirely with the venue or event organiser:

- **Private events** (family gathering, class reunion, private party) — no public performance licence is required in most jurisdictions.
- **Public venues** (bars, restaurants, clubs) — a blanket PRO licence (ASCAP/BMI/SESAC in the US, PRS/PPL in the UK, etc.) is required for any public music playback, with or without JukeBar. Most licensed venues already pay this annually (~$500–1,500/yr). JukeBar adds no new obligation.
- **Own content** — venues may load their own purchased MP3s into an Apple Music library and use those as the playlist. PRO licensing still applies for public performance.
- **Apple Music for Business** — Apple's commercial tier includes PRO licensing through Apple's own agreements. Venues using this tier are covered.

App Store description must include: *"JukeBar requires an Apple Music library containing the songs you wish to play. Venue operators are responsible for any applicable public performance licences."*

## Visual Identity

Both the customer web app and the host KioskView share the grapefruitplayer brand:

- **Logo:** grapefruit cross-section (orange skin, white pith, coral flesh, 16 segment lines). Inline SVG in HTML; SwiftUI `Canvas` on the host.
- **Title:** "JukeBar [bar name]" with each letter in a random color from `[#fda185, #fbbe84, #ffc24a, #dc7955, #e8406a, #ffffff]`, no two adjacent the same. Bubblegum Sans font in the web app; system `.heavy` on the host.
- **Accent colors:** `#fda185` (coral) for interactive elements, `#dc7955` (darker coral) for primary buttons, `#fbbe84` (orange) for subtitle/info text.
- **Backgrounds:** `#1a1a1a` body, `#111` header, `#1e1e1e` cards/panels.
